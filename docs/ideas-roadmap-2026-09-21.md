## 0. 查证结论（方案的事实基础）

| 系统 | 位置 | 技术栈 | 说明 |
|------|------|--------|------|
| **nexus-core** | `/root/nexus-core`（pm2 `nexus-api`:3458） | 单文件 `index.html`（~5900 行）+ Express + SQLite | 主工作台。4 个 tab：今日 / 课表 / 账本 / 我的 |
| **reader** | `/opt/reader`（pm2 `reader`:8080） | NestJS 后端 + Vite/TS 前端（AGPL 开源） | 独立阅读器，前端是构建产物 |
| **guide** | `/var/www/guide` | 静态镜像 | 与本次需求无关 |

**nexus-core 新增功能的固定套路**（三条缺一不可）：
1. `index.html` 里加 HTML 容器（放进某个 panel，或新增 panel + tab）
2. 写 `renderXxx()` 函数
3. 在 `renderPanel(name)`（L3277）里注册

**数据层**：`Store.get/set` 读 localStorage → 经 `KVSync` 防抖推到服务器 `/api/kv`（key 名即数据名）。新增数据 = 新 key，无需改后端。

**关键取舍**：底部只有 4 个 tab，手机宽度已接近上限。**新模块优先嵌入现有面板**（尤其「今日」），而不是加第 5 个 tab。

## 需求 1：直播切片时间线 —— 详见下方「规划」

> 「我想加一个直播切片的时间线，感觉会很萌啊，然后可以加一个中间隔了多少天那种，就类似于历史时间线的感觉」

**先确认再动手**：这条需求方向最模糊（见末尾待拍板问题 ①），先出规划、对齐后再实施。

### 1.1 目标与产物
一个「纵向时间线」视图：按时间倒序展示条目，每条之间显示**间隔天数**（"距上一条 12 天"），移动端单手可滑。

### 1.2 前置对齐（必须先答）
- 「直播切片」到底是：
  - (a) **bilibili/抖音的切片视频收藏**（有链接、有 UP 主）？
  - (b) 你自己记录的**直播事件日志**（某天谁直播了什么）？
  - (c) 别的意思？
- 这决定数据模型。先别开工，等你一句话。

### 1.3 数据模型（草案，假设是 (a)）
```
timeline: [{
  id, date,            // YYYY-MM-DD，时间线主轴
  title,               // 切片标题
  link,                // 站外链接（渲染走 safeUrl 白名单）
  cover,               // 可选，复用 /api/files 上传
  tags: [], note,      // 备注
  createdAt
}]
```

### 1.4 放置位置（三选一，见待拍板 ⑤）
- **A. 嵌入「今日」面板**：符合"顺手看到"，但今日面板已经很长
- **B. 新增第 5 个 tab**：底部导航变挤（4→5）
- **C. 挂在「我的」面板里做二级页**：不占导航，但要多点一次

### 1.5 分阶段实施
| 阶段 | 内容 | 产出 |
|------|------|------|
| ① 骨架 | 容器 + `renderTimeline()` + 数据模型 + 注册 renderPanel | 手工塞数据能看到时间线 |
| ② 最小闭环 | 手动新增/编辑/删除条目（沿用「随手记」的交互范式） | 能自己录、能删改 |
| ③ 间隔天数 | 相邻条目差值的计算与展示（"距上一条 N 天"） | 时间线有"时间感" |
| ④ 视觉打磨 | 轴线 + 节点 + 卡片 + 折叠（复用现有折叠范式） | "萌" |
| ⑤ 可选 | 封面图、标签筛选、点开跳原站 | 增值 |

### 1.6 复用存量
- 折叠交互：抄「交易记录」「每日统计」的 `<details>` 折叠范式
- 链接安全：渲染一律走 `safeUrl()`（阶段 5 安全审查新增）
- 图片：复用 `/api/files` 上传通道

### 1.7 风险
- 间隔天数在**跨月/跨年**时要用日期差实数（`(a-b)/86400000`），不能按"月"糊算
- 条目多了要分页或折叠，否则首屏拉长——**别让今日面板变成第二个账本**

## 需求 2：每日英语单词 / 短句

> 「每天认识一个英语单词、一句英语短句……做到自己的个人网站上，看课表、记录支出、看小说的时候顺手就看到了」

### 2.1 动手方案

**位置**：嵌入「今日」面板（新增一个 `daily-section`）。这是需求原文直接指定的——"顺手看到"。

**数据源**（关键约束）：
- 词库需要一份静态数据：单词 + 音标 + 释义 + 例句；短句库：英文 + 中文
- 来源二选一：**我内置一份**（如 CET-4 常用词 365 条 + 365 句，我手写/整理）；**你给我一份**（质量更高、更合口味）
- 存为 `index.html` 内的常量数组（不占 KV、不需后端），或独立 JSON
- 体量估算：365 词 × 约 100 字 ≈ 36 KB，可接受

**轮换逻辑**：
```
dayIndex = 自某个固定基准日的天数差
word = WORDS[dayIndex % WORDS.length]
sentence = SENTENCES[dayIndex % SENTENCES.length]
```
- 天然幂等（同一天任何人任何设备看到同一条）、无需存状态、可回溯（"昨天/前天"也能算出来）
- 复用现成的 `localDate()` / `TODAY()` 日期工具（已统一口径）

**渲染**：卡片式，沿用 `.daily-section` 样式；展示 单词 / 音标 / 词性+释义 / 例句（中英）。

**分阶段**：
| 阶段 | 内容 |
|------|------|
| ① 最小闭环 | 静态词库 + 按日期取模 + 卡片渲染（**只读**） |
| ② 发音 | 点击发音（浏览器 `speechSynthesis`，约 3 行，零依赖、免费离线） |
| ③ 记忆 | "认识 / 不认识"标记 + 存 KV + 隔天复习（间隔重复，类似 Anki 简化版） |
| ④ 历史 | 可回看前 7 天的内容 |

### 2.2 待拍板

- 短句类型：日常口语 / 名言 / 商务？
- 要不要发音（阶段②）？

## 需求 3：小说听书 —— **不用开发，功能已内置，只差配置**

> 「想给小说加一个听书功能……我不确定这个功能怎么实现会比较好，因为人声的选择也很重要」

### 3.1 查证结论（这条是本次最大的意外收获）

**reader 项目本身已内置完整听书能力**：

| 层次 | 文件 | 作用 |
|------|------|------|
| 前端朗读 | `web/src/render/tts.ts`、`tts-text.ts`、`speech.ts` | 逐句朗读、断句、推进 |
| 前端控制条 | `web/src/ui/reader-chrome.tsx` | 播放/暂停/语速等 UI |
| 前端设置 | `web/src/store/settings.ts` | `ttsEngine` / `ttsVoice` / `ttsRate` / `ttsPitch` / `ttsAutoAdvance` |
| 后端代理 | `server/src/services/tts.ts` | **只代理不合成**，`TTS_URL` 指向外部 TTS 服务 |
| 后端接口 | `server/src/http/routes/tts.ts` | `GET /api/v1/tts/voices`（能力）、`GET /api/v1/tts`（音频） |

引擎可选四种：`auto | system | http | native`
- `system`：用**手机/浏览器自带语音**（iOS Safari 的中文语音质量一般 → 这正是你说的"人声很重要"的痛点）
- `http`：走**服务端代理**，可接任意高质量 TTS（**当前未启用**）

**当前状态**：`/opt/reader/ecosystem.config.js` 的 `env` 里**没有 `TTS_URL`** → 源码注释明确写 "`TTS_URL` unset means no HTTP engine" → 所以现在只能用系统语音。

### 3.2 动手方案（成本极低）

1. 服务器部署一个 TTS 服务（选型见下）
2. 在 `ecosystem.config.js` 的 `env` 加 `TTS_URL=http://127.0.0.1:<port>`
3. `pm2 restart reader`
4. 进阅读器设置 → 选 voice（会从 `/api/v1/tts/voices` 拉到列表）

**TTS 选型**：

| 方案 | 音质 | 成本 | 代价 |
|------|------|------|------|
| **edge-tts**（推荐） | 高（微软 Azure 语音，中文"晓晓/晓伊"很自然） | 免费 | **需联网**（调微软接口），有被限流风险 |
| Piper（本地模型） | 中上 | 免费 | 吃 CPU/内存（阿里云小机器要掂量），需下模型 |
| 商业 API（阿里/腾讯云） | 高 | 按量付费 | 要钱、要 key |

> 接口形状：reader 要求服务接受经典的 `?text=...&speed=...` 形态——edge-tts 需要套一层极薄 HTTP wrapper（几十行），或找现成的兼容镜像。

### 3.3 分阶段
| 阶段 | 内容 |
|------|------|
| ① | 装 edge-tts + 起 wrapper 服务 + 配 `TTS_URL` + 重启（最小闭环） |
| ② | 逐条试听候选中文 voice，定一个（"人声选择"落地） |
| ③ | 调 `ttsRate`（语速）、开 `ttsAutoAdvance`（自动翻页/连读），睡前场景调优 |
| ④ | 可选：给常看的书预生成音频缓存（`tts.ts` 已带缓存逻辑，看 `x-tts-cache` 头） |

### 3.4 风险与注意
- **AGPL 项目**：自用改配置没问题；别把它改完对外提供服务
- **联网依赖**：edge-tts 断网即失效 → 若你在意，走 Piper（代价是 CPU）
- **别自己造轮子**：绝不要从零写朗读功能，已有全套

## 需求 4：课表课程名简写

> 「课表那个页面毛概和习概可以简写……包括其他课程也是，比如数据结构就直接叫数据结构、Python 就叫 Python，全名显示很臃肿」

### 4.1 现状（已查证）

课程名在 **5 处**裸渲染（`index.html`）：

| 行 | 函数 | 场景 |
|----|------|------|
| L5611 | `courseRow()` | 预告视图 |
| L5688 | `renderCourseDay()` | 日视图课程卡 |
| L5714 | `renderCourseWeek()` | 周视图（格子内 + `title` 属性） |
| L5746 | `renderNextClassBanner()` | 今日面板「下一节」 |

数据源：`DEFAULT_COURSES`（内置）+ `Store('courses')`（用户导入）+ `SCHEDULE_OVERRIDES`（临时补课）。全名如「毛泽东思想和中国特色社会主义理论体系概论」。

### 4.2 方案对比

**方案 A（推荐）：简称映射表 + 渲染函数**
```js
const COURSE_SHORT = {
  '毛泽东思想和中国特色社会主义理论体系概论': '毛概',
  '习近平新时代中国特色社会主义思想概论': '习概',
  'Python语言程序设计': 'Python',
  '概率论与数理统计': '概率论',
  ...
};
function shortCourseName(n) { return COURSE_SHORT[n] || n; }
```
- 渲染 5 处统一改调 `shortCourseName(c.name)`
- **不动课程数据** → 零迁移、不影响 Store/KV/导入格式、对你已导入的课表也生效
- 查不到就回退原名 → 安全，不会因为漏配而显示空白

**方案 B：给课程数据加 `shortName` 字段** ❌
- 要改内置数据 + 导入格式 + 对 Store 里已有数据做迁移 → 复杂度不对等，不做

### 4.3 边界与决策点
- 周视图格子窄，本来就该短；日/预告视图空间大
- **建议：全视图统一用简称**，并在周视图保留 `title` 全名（鼠标悬停可见）——`title` 属性现已存在（L5714），改成简写后 `title` 仍放全名即可
- 待拍板：日视图要不要保留全名？（个人倾向统一简写，既然你说"臃肿"）

### 4.4 工作量
**小**：1 个常量 + 1 个函数 + 5 处调用替换。无数据风险。

## 需求 6：象棋残局学习（一天一残局）

> 「想加入一个象棋残局学习，一天一个残局……因为我玩勾勾象棋有体力限制，一天可能只能过一个残局」

### 6.1 动手方案

**位置**：嵌入「今日」面板（同需求 2，每日内容、顺手可见）。

**数据（关键约束）**：每个残局需要
```
{ id, name, fen, solution: ['着法1','着法2',...], difficulty, hint }
```
- 来源：**我内置一份**（30~50 个经典残局，逐条录 FEN + 解法）——可控、离线、无版权风险
- 或找开源中国象棋残局库（注意处理来源与授权）

**棋盘渲染（纯前端，零依赖）**：
- 9 列 × 10 行交叉点，用 CSS Grid + 绝对定位画线
- 棋子用汉字「帅仕相马车炮兵 / 将士象马车炮卒」+ 圆形样式
- ⚠️ **不要引国际象棋的库**（`chess.js` 之类是 Chess 不是 Xiangqi，规则完全不同）

**轮换**：按日期取模（同需求 2 的 `dayIndex % N`）。

**分阶段**：
| 阶段 | 内容 | 复杂度 |
|------|------|--------|
| ① | 静态棋盘渲染 + 每日残局展示（**只读**，看局面 + 看解法） | 小 |
| ② | 走子交互：点选起点/终点 → 校验合法性 → 判断对错 | **中**（最重的部分） |
| ③ | 解法逐步演示（"下一步"按钮，动画） | 中 |
| ④ | 战绩记录（已解/未解，存 KV）+ 连对天数 | 小 |

**阶段②的本质难点**（要有心理准备）：
需要一个中国象棋**走法校验器**，覆盖：马蹩腿、象塞眼、士象不过河、兵过河后可横走、炮隔子吃、将帅照面禁手、被将军时不能走无关子。纯前端可写，约 150~250 行，但**是最容易出 bug 的地方**，必须配测例。

### 6.2 待拍板
- 你要的是 **(a) 只看局面 + 看解法**（学习向），还是 **(b) 能自己走子对弈判定**（练习向）？
- 前者 1 个阶段就能上；后者多 1 个硬骨头（校验器）。
